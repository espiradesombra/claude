1. QUÉ QUERÍA EL CHAT (INFERENCIA)
--------------------------------------------------------------------------------

El diálogo no pedía un solo programa. Pedía demostrar que:

  a) La red deja de ser transporte y pasa a ser cómputo distribuido.
  b) La ALU del maestro se alivia desplazando HASH/INDEX/QUERY a hubs.
  c) El conocimiento derivado (K(N)) es reutilizable — segunda consulta ~O(1).
  d) Grafcet + existencia + redundancia reducen sincronización.
  e) El sistema es industrial: determinista, auditable, sin malloc en bucle
     crítico (K3 C), perfiles de ejecución, permisos de red.

ChatGPT proponía 4 experimentos medibles. AntiPC los implementa como A→E.
La v0.1.0 añade Flow Kernel. Esta capa industrial añade el caso de fábrica.


2. ARQUITECTURA INDUSTRIAL IMPLEMENTADA
--------------------------------------------------------------------------------

  ExecutionProfile     Perfiles: portable, server, cluster, laboratory, industrial_audit
  KnowledgeResolver    resolve(sig) → FOUND_LOCAL | EXECUTE | WAIT (v0.0.064)
  PluginManager        UPS v0.0.065 — registro, métricas, API version
  IndustrialTelemetry  CSV + JSON para auditoría / SCADA / laboratorio
  Worker pool          scan_files() — hubs simulados con ThreadPoolExecutor

  Plugins industriales:
    K3_FILE            Huella fichero (tamaño + hash HASHTOOLCODE)
    K3_DEDUP           Agrupación duplicados (lógica k3dedup.c)
    K3_HASH            Transformación en grafo de flujo


3. CASO DE USO INDUSTRIAL
--------------------------------------------------------------------------------

  Problema de fábrica / servidor de archivos:
    - Auditar integridad de miles de ficheros de configuración
    - Detectar duplicados antes de backup o sincronización
    - Segunda pasada debe costar menos (conocimiento ya en buffer)

  Pipeline:
    Ruta fichero → K3_FILE → Knowledge Resolver → (reuse | execute)
                 → K3_DEDUP → informe bytes recuperables

  Comparación:
    Monolítico     : hash secuencial, sin caché, 100% ALU cada vez
    Industrial     : resolver + workers + K(N)
    2ª pasada      : demuestra reutilización (objetivo del chat)


4. PERFILES DE EJECUCIÓN (gptcomputing v0.0.06)
--------------------------------------------------------------------------------

  portable()         Battery optimizer ON, red OFF
  server()           Distribuido ON, publicar conocimiento
  cluster()          Red ON + permisos + distribuido
  laboratory()       Research mode — fuerza ejecución (validar hipótesis)
  industrial_audit() Distribuido + benchmark + telemetría

  Separación clave del chat:
    Runtime Mode ≠ Network Mode
    Un perfil combina capacidades; no hay un solo "modo".


5. LEYES AntiPC CUMPLIDAS EN CÓDIGO
--------------------------------------------------------------------------------

  Inmutabilidad        Reference frozen
  Determinismo         Plugins pure (K3_FILE, K3_HASH)
  Consulta previa      KnowledgeResolver antes de execute
  Activación por evento EventBus (no polling)
  Neutralidad núcleo   Flow Kernel no conoce HASH — solo plugins
  Publicación          knowledge.publish() tras execute
