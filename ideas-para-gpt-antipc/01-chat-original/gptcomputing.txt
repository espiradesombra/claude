PayloadStore.cpp
#include "PayloadStore.h"

namespace antipc
{

PayloadID PayloadStore::store(std::vector<uint8_t>&& data)
{
    PayloadID id = m_nextId++;

    m_storage.emplace(id,std::move(data));

    return id;
}

const std::vector<uint8_t>* PayloadStore::get(PayloadID id) const
{
    auto it = m_storage.find(id);

    if(it==m_storage.end())
        return nullptr;

    return &it->second;
}

bool PayloadStore::exists(PayloadID id) const
{
    return m_storage.contains(id);
}

void PayloadStore::remove(PayloadID id)
{
    m_storage.erase(id);
}

std::size_t PayloadStore::size() const
{
    return m_storage.size();
}

}

AntiPC

Adaptive Network Through Parallel Computing

Declaración de propósito

AntiPC es un proyecto de investigación e ingeniería cuyo objetivo es explorar un nuevo modelo de ejecución de software basado en el conocimiento reutilizable en lugar del cálculo repetitivo.

La idea central es que, antes de ejecutar una operación, el sistema determine si ese conocimiento ya existe y puede reutilizarse de forma segura. Solo cuando no exista una respuesta válida, la operación será ejecutada por los recursos de cálculo disponibles.

AntiPC propone un microkernel orientado a eventos donde CPU, GPU, aceleradores, memoria compartida, almacenamiento y red forman parte de un mismo entorno de ejecución mediante un modelo unificado de referencias y conocimiento.

Significado del nombre

AntiPC significa:

Adaptive Network Through Parallel Computing

El nombre refleja los cuatro pilares fundamentales del proyecto:

Adaptive: el sistema adapta dinámicamente sus decisiones de ejecución según el contexto, la disponibilidad de recursos y el conocimiento existente.
Network: la red es un recurso opcional que permite compartir conocimiento entre nodos autorizados, ampliando la capacidad del sistema sin modificar los programas.
Through: representa la integración de todos los componentes mediante un flujo único de ejecución basado en referencias, eventos y transformaciones.
Parallel Computing: las operaciones pueden ejecutarse en paralelo siempre que sus dependencias lo permitan, aprovechando CPUs, GPUs, aceleradores u otros nodos de ejecución.
Objetivo

El objetivo de AntiPC no es sustituir los sistemas operativos actuales ni reemplazar la CPU.

Su objetivo es construir un Runtime de Conocimiento capaz de:

reutilizar resultados previamente obtenidos;
evitar cálculos redundantes;
distribuir trabajo cuando exista autorización;
desacoplar el almacenamiento del conocimiento de su ejecución;
proporcionar una plataforma extensible mediante plugins independientes;
escalar desde un único ordenador hasta una red distribuida utilizando la misma arquitectura.
Filosofía

En un sistema convencional, el cálculo es el recurso principal.

En AntiPC, el recurso principal es el conocimiento.

La ejecución deja de ser la primera opción y pasa a convertirse en el último recurso cuando no existe una respuesta reutilizable.

Principios fundamentales
Todo conocimiento es inmutable.
Toda transformación genera una nueva referencia.
El Runtime nunca interpreta el significado de una operación; únicamente coordina su ejecución.
La comunicación distribuida siempre requiere autorización explícita.
La red es una capacidad opcional del sistema, nunca un requisito.
Los plugins amplían el Runtime sin modificar el núcleo.
El conocimiento puede almacenarse en distintos niveles (RAM, almacenamiento local o nodos autorizados) sin alterar el modelo de ejecución.
Todas las decisiones se toman a partir de referencias, eventos y conocimiento disponible.
Estado del proyecto

AntiPC se encuentra actualmente en fase de investigación y desarrollo. La arquitectura se construye siguiendo una evolución incremental, donde cada versión incorpora componentes funcionales verificables y medibles antes de añadir nuevas capacidades.

Creo que este texto tiene un tono apropiado para un proyecto serio: explica la visión, define las siglas, fija el objetivo y evita afirmar beneficios que todavía no han sido demostrados experimentalmente. Si más adelante los benchmarks muestran mejoras de rendimiento o eficiencia energética, esas afirmaciones podrán añadirse como resultados, no como promesas.

class KnowledgeRouter
{
public:

private:

    Resolution searchNetwork(const Signature&);

KnowledgeRouter.cpp

Lo primero será muy sencillo.

Resolution KnowledgeRouter::resolve(const Signature& s)
{
    Resolution r;

    r = searchRam(s);

    if(r.found)
        return r;

    r = searchKnowledge(s);

    if(r.found)
        return r;

    r = searchPayload(s);

    if(r.found)
        return r;

    r = searchShared(s);

    if(r.found)
        return r;

    r = searchNetwork(s);

    if(r.found)
        return r;

    r.source = ResolutionSource::ExecutePlugin;

    return r;
}

Mi propuesta final

Quiero introducir una norma que creo que hará el proyecto muy sólido:

Ningún componente entra en AntiPC porque "suena bien". Entra porque supera una prueba, tiene una especificación y demuestra aportar valor medible.

Eso también se aplica a nuestras propias ideas. Si la Regla Mecánica, K3-Toffoli o un futuro WaveProvider muestran ventajas objetivas en benchmarks, pasan de research/ a plugins/. Si además se convierten en una pieza esencial y estable, entonces podrán formar parte del núcleo.
